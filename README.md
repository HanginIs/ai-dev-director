# AI Dev Director · HanginIs 수정판

[한국어](README.md) · [English](README.en.md)

로그인해 둔 AI 코딩 CLI(Claude Code, OpenAI Codex, 선택 사항으로 Google Antigravity)를 HEAD·BUILDER·REVIEWER로 나눠 돌려, 목표 한 줄을 테스트와 독립 리뷰를 거친 코드로 바꾸는 로컬 개발 감독 도구입니다. 종량제 API는 쓰지 않습니다.

이 저장소는 [DAVZD의 ai-dev-director](https://github.com/digilogd-cmd/ai-dev-director) v3.1.8을 macOS에서 쓰도록 고친 포크이며, 원본 v3.2.0의 안전 수정(2026-11-21)을 반영했습니다. 원본은 Windows 우선이고, 이 포크는 macOS 전용 앱을 더하고 결과 반영·미션 판정·저장소 처리를 보강했습니다.

- **상태:** macOS에서 매일 사용합니다. 2026-11-23 DB·검증 캐시·한도 일시정지·오류 전달 보완 후 전체 기본 회귀 검사 859개 통과·Windows 전용 1개 건너뜀. 실제 AI·별도 실행 대시보드 선택 검사 2개는 제외했습니다.
- **미검증:** 이 포크의 변경분은 Windows와 Linux에서 실행해 보지 않았습니다. TRIAD의 세 CLI 실호출 전체 흐름도 아직 검증하지 않았습니다.

## 하는 일

```
목표 ─▶ HEAD (작업 명세 ORDER 작성) ─▶ BUILDER (파일 변경안을 JSON으로 제출)
              ▲                                   │
              │                                   ▼
        HEAD 판정 ◀── REVIEWER ◀── 검증 (격리 작업본에서 빌드·테스트)
```

- **역할:** 기본값은 HEAD와 BUILDER가 Codex, REVIEWER가 Claude Code입니다. 리뷰어가 작업을 계획하고 만든 쪽과 다른 AI가 되도록 나눴습니다. Antigravity가 꺼져 있으면 두 CLI가 세 역할을 나눠 맡고, BUILDER와 REVIEWER만 서로 달라야 합니다. 한 CLI가 한도에 걸리거나 실패하면 다른 CLI로 넘어갑니다.
- **미션:** 채팅 한 줄이 미션이 됩니다. HEAD가 단계(마일스톤)를 하나씩 계획하고, 각 단계의 테스트·리뷰 결과를 보고 다음 단계를 다시 계획합니다.
- **TRIAD 연구:** 작업실 → TRIAD 연구에서 주제를 입력하고 참여 AI를 두 개 이상 체크한 뒤 **연구 시작**을 누릅니다. 선택한 AI가 독립 제안과 교차 비평을 수행합니다. Codex를 선택하면 Codex가, 그 외에는 Claude Code가 가설을 합성합니다. 연구는 임시 작업공간에서 가설 합성까지 진행하며, **작업 정지**로 중단할 수 있습니다.
- **격리:** 모든 변경은 프로젝트 안 `.director_worktrees/`의 git 작업본에서만 이뤄집니다. 프로젝트 원본은 미션이 끝난 뒤 반영 단계에서만 바뀝니다.
- **반영:** 기본값은 결과를 보고 직접 **반영**을 누르는 방식입니다(`autonomy.auto_apply: "off"`). `on_pass`나 `on_done`으로 바꾸면 통과한 결과를 자동 반영합니다. 반영 뒤 프로젝트에서 테스트를 다시 돌리고, 실패하면 되돌립니다. 커밋은 하지 않습니다.

## 요구 사항

- macOS 13 이상
- Python 3.9 이상, Git
- 앱을 빌드하려면 Xcode(Swift 5.9 이상)
- 로그인된 CLI 두 개 이상: `claude`(Claude Code 2.1.259 이상), `codex`, `agy`. 구독 로그인 세션을 그대로 씁니다. API 키는 필요 없고, 환경 변수에 있어도 CLI를 부르기 전에 지웁니다. 다만 **CLI 자체를 API 키로 로그인해 두었다면 그 키로 과금됩니다.**
- **Antigravity(`agy`) 주의:** 구글 Antigravity FAQ는 `agy`를 다른 애플리케이션 안에 감싸 쓰는 것을 소비자 플랜에서 지원하지 않는다고 적고 있고, 계정 정지 사례도 보고됩니다. 그래서 원본 v3.2.0처럼 **기본으로 꺼 두었습니다.** 위험을 감수하고 쓰려면 작업실 화면의 **Antigravity 꺼짐 · 켜기** 버튼을 누르거나(경고를 한 번 확인합니다) `config.local.yaml`에 `antigravity: {enabled: true}`를 적으세요. 콘솔 스위치(`data/antigravity.json`)가 설정 파일보다 우선합니다. 켜면 두 역할을 맡던 AI의 BUILDER가 Antigravity로 가고, 끄면 Antigravity의 역할이 BUILDER와 REVIEWER가 서로 다르게 Claude나 Codex로 돌아갑니다. 그때부터 역할을 Antigravity에 줄 수 있고 세 AI TRIAD 연구가 됩니다. 저장해 둔 역할에 Antigravity가 있는데 꺼져 있으면 그 저장값은 무시하고 `config.yaml`의 역할을 씁니다.

## 설치와 실행

```bash
python3 -m venv .venv
./.venv/bin/python -m pip install -r requirements.txt
./script/build_and_run.sh              # dist/AI-Dev-Director.app을 만들고 실행
./script/build_and_run.sh --build-only # 빌드만
```

앱은 서버를 자동으로 띄우고 콘솔을 창에 보여 줍니다. 콘솔 연결(아래 브라우저의 연결 주소)도 앱이 알아서 합니다. 빌드할 때 저장소의 절대 경로를 기억하므로, 저장소를 옮겼다면 다시 빌드하세요. 앱 자체는 응용 프로그램 폴더로 복사해도 됩니다.

- **프로젝트 선택:** 보기 → 프로젝트 폴더 선택(⌘O). macOS 기본 폴더 선택 창이 열립니다.
- **종료:** 종료할 때 "백그라운드 계속 실행"(창만 닫고 서버와 작업 유지)과 "작업 중지 후 종료" 중에서 고릅니다.
- **연결이 끊겼을 때:** 보기 → 콘솔 다시 연결(⌘R).

앱 없이 쓰려면 서버만 띄우고 브라우저로 엽니다.

```bash
./start-companion.sh    # 연결 주소(http://127.0.0.1:8081/?token=...)를 출력합니다
./stop-companion.sh
```

처음 한 번은 **출력된 연결 주소**로 접속하세요. 그 브라우저는 이후 `http://127.0.0.1:8081`(스테이지 화면)과 `/classic`(작업실 화면)이 바로 열립니다. 연결하지 않은 브라우저와 프로그램은 콘솔을 열거나 명령을 보낼 수 없습니다. 연결 주소는 `./.venv/bin/python companion_server.py --login-url`로 다시 볼 수 있습니다.

터미널에서 바로 미션을 돌릴 수도 있습니다.

```bash
./.venv/bin/python director.py do "로그인 버그 고쳐" -p /path/to/project --profile quick
./.venv/bin/python director.py status
./.venv/bin/python director.py clean-worktrees -p /path/to/project --dry-run
```

`do`는 서버가 떠 있으면 서버를 통해 미션을 시작해 콘솔에 보이게 하고, 서버에 연결할 수 없을 때만 그 자리에서 실행합니다. `--no-apply`를 주면 어느 쪽이든 결과를 작업본에만 두고 프로젝트에는 반영하지 않습니다.

서버는 `solomon.allowed_roots`에 적힌 폴더 아래의 프로젝트만 받습니다. `config.yaml`의 기본값은 원본의 Windows 경로이므로, `config.local.yaml`에 프로젝트들의 상위 폴더를 적어야 합니다(아래 설정 예시). 서버가 요청을 거절하면(허용 폴더 밖, 다른 미션 진행 중 등) `do`는 이유를 출력하고 끝내며, 터미널에서 대신 실행하지 않습니다.

## 미션 결과 읽기

미션이 끝나면 메시지 하나에 결과와 반영 여부가 함께 나옵니다.

| 상태 | 뜻 |
| --- | --- |
| 미션 완료 (DONE) | HEAD가 목표를 달성했다고 판정했고, 통과한 단계가 하나 이상 있습니다. |
| 미션 중단 - 단계 예산 소진 또는 계획 불가 (INCOMPLETE) | 단계 예산을 다 썼거나, HEAD는 완료라고 했지만 통과한 단계가 없습니다. |
| 미션 실패 (FAILED) | 연속 실패 한도에 걸렸거나, 검증 명령 자체가 같은 이유로 두 번 연속 실패했습니다. |
| 미션 보류 - 사용자 결정 필요 (BLOCKED) | 결제·실계좌 주문·실제 자격증명·되돌릴 수 없는 외부 행동처럼 사람이 정해야 하는 일을 만났습니다. |
| 미션 일시정지 - AI 사용 한도 (BLOCKED) | 실제 CLI 오류로 한도 중단이 확인됐습니다. 자동 재개하지 않으며, 한도가 풀리면 **이어서 진행**으로 같은 단계를 새 실행합니다. |
| 정지 (STOPPED) | 사용자가 멈췄습니다. 다시 켜도 스스로 재개하지 않습니다. |

반영 결과는 마지막 줄에 나옵니다.

사용 한도 대기는 일반 코드 실패·로그인 오류·사용자 승인 대기와 구분합니다. 재개해도
단계 번호와 작업 지시는 유지하고, 이전 실행 ID와 미검수 작업본은 보존합니다. 이전에
검증을 통과한 상태에서 같은 단계를 다시 실행하므로, 미검수 변경을 승인된 결과처럼
사용하거나 원본 프로젝트에 자동 반영하지 않습니다. 한도에서 복구된 뒤라도 기존
검증·독립 리뷰·보안 관문을 다시 통과해야 합니다. 과거 오류 기록을 소급 추정하지 않으며,
새 CLI 기록의 오류 분류만 추가합니다(원문 오류·인증정보는 저장하지 않음).

같은 단계를 새 실행으로 재개하는 접근은 [eunsebi 수정판](https://github.com/eunsebi/ai-dev-director/commit/4f5d3d1395e091dcd59d5d64cac331cbc7a18da3)을
참고했습니다. 이 포크에서는 실행별 실제 오류 분류, 보안 관문 우선, 미검수 작업본 보존과
한도 대기 중 자동 반영 차단을 함께 적용했습니다.

- **"결과물을 프로젝트에 적용했습니다":** 파일을 프로젝트에 썼고, 프로젝트에서 테스트를 다시 통과했습니다.
- **"적용할 변경이 없습니다":** 확인만 하고 고칠 것이 없었거나, 프로젝트가 이미 같은 내용입니다. 오류가 아닙니다.
- **"자동 적용하지 않았습니다 (이유)":** 충돌, 검증 안 함, 검수 뒤 작업본 변경 등으로 반영을 보류했습니다. 작업본은 남아 있고, 콘솔에서 직접 반영하거나 폐기할 수 있습니다.

통과한 결과물이 있으면 그 앞줄에 **"미션 전체 변경: N개 파일 (새 파일 M개), +A줄 / -B줄"**이 나옵니다. 여러 단계를 합친 양이며, 한 단계 상한을 넘으면 직접 확인하라는 문구가 붙습니다. 표시만 하고 막지는 않습니다.

## 지키는 규칙

| 규칙 | 동작 |
| --- | --- |
| 종량제 API 차단(환경 변수 범위) | 모든 `*_API_KEY`와 인증 토큰, 엔드포인트·클라우드 과금 전환 변수(`ANTHROPIC_BASE_URL`, `CLAUDE_CODE_USE_BEDROCK` 등)를 지운 뒤 CLI와 검증 명령을 실행합니다. CLI를 API 키로 로그인해 둔 경우는 막지 못합니다. |
| 원본 격리 | 빌드와 수정은 `.director_worktrees/`의 작업본에서만 합니다. |
| 읽기 전용 역할 | HEAD와 리뷰어는 파일을 쓰거나 명령을 실행할 수 없습니다. Codex는 읽기 전용 샌드박스로, Claude Code는 읽기 도구(Read, Grep, Glob)만 주고 연결 앱 도구와 프로젝트 쪽 설정 파일을 빼고 실행합니다. |
| 범위 제한 | ORDER에 적힌 허용 경로·보호 경로·파일 수·변경 줄 수를 Director가 검사합니다. BUILDER는 이를 완화할 수 없습니다. 파일 수·변경 줄 수를 넘으면 그 단계는 멈추고 미션이 더 작은 단계로 다시 계획하며, 의존성·빌드·권한 설정 파일을 바꾸면 사용자 결정을 기다립니다. HEAD가 대신 통과시키게 하려면 `autonomy.waive_scope_caps: true`로 직접 켜야 합니다. |
| 프로젝트 밖 문서 | ORDER에 적힌 절대 경로 문서는 프로젝트 안이거나 `safety.reference_roots`에 적은 폴더 안에 있을 때만 BUILDER에 넘깁니다. |
| 콘솔은 연결된 화면만 | 상태를 바꾸는 모든 요청에 로컬 출처 검사와 함께, 연결 주소로 받은 세션이나 브리지 토큰이 필요합니다. 토큰은 연결하지 않은 요청에 내주지 않습니다. |
| 리뷰 실패는 실패 | 리뷰 응답이 없거나 깨지면 통과가 아니라 실패로 처리합니다. |
| 검수한 것만 반영 | 통과 시점의 파일 내용을 기록해 두고, 반영 직전에 작업본과 대조합니다. 검수 뒤에 바뀐 작업본은 반영하지 않습니다. |
| 사용자 편집 우선 | AI와 사용자가 같은 파일을 고쳤으면 충돌로 막습니다. 사용자가 지운 파일을 되살리지 않고, 삭제는 반영하지 않습니다. |
| 검증 안 한 결과는 사람이 | 빌드·테스트가 하나도 실행되지 않은 결과는 자동 반영하지 않습니다. 콘솔에서 사람이 직접 반영할 수 있습니다. |
| 돈과 자격증명은 사람이 | 결제, 실계좌 주문 코드, 계정 생성, 되돌릴 수 없는 외부 행동에서 멈춥니다. |
| 정지는 정지 | 채팅의 "중단"·"멈춰"·"stop"이나 콘솔의 작업 정지 버튼은 그 미션이 띄운 CLI를 바로 끝냅니다. 정지된 미션은 새 CLI 호출을 시작하지 않고, 완료로 바뀌지 않으며, 결과가 반영되지 않습니다. 다른 미션은 계속 돕니다. |
| 저장소 안에 저장소 금지 | 이미 다른 git 저장소 안에 있는 폴더를 프로젝트로 지정하면 새 저장소를 만들지 않고, 저장소 루트를 지정하라고 안내합니다. |
| 프로젝트가 아닌 폴더 거절 | 다운로드·데스크탑·문서 폴더 자체, 응용 프로그램·라이브러리 폴더와 그 아래, 앱 번들(.app)이 들어 있는 폴더는 프로젝트로 받지 않습니다. git 저장소도 작업본도 만들지 않고 전용 폴더로 옮기라고 안내합니다. 사용자가 직접 git 저장소로 만든 폴더는 그대로 받습니다. |

## 검증 명령

프로젝트마다 어떤 명령으로 검증할지는 다음 순서로 정합니다.

1. `config.yaml` 또는 `config.local.yaml`의 `projects`에 등록한 명령
2. `tests/` 폴더에 파이썬 테스트 파일이 있으면 pytest (프로젝트에 pytest 설정이 없으면 상위 폴더의 `pytest.ini`를 쓰지 않습니다)
3. `Package.swift`에 테스트 대상이 있으면 `swift test`
4. `package.json`에 test 스크립트가 있으면 `npm test`
5. `Tests/run.sh`, `tests/run.sh`, `test/run.sh`가 있으면 그 스크립트
6. `Makefile`에 `test` 대상이 있으면 `make test`

폴더 이름은 대소문자를 정확히 구분합니다. macOS 기본 디스크는 대소문자를 구분하지 않지만, Swift의 `Tests/` 폴더를 파이썬 `tests/`로 보지 않습니다.

아무것도 찾지 못하면 아무것도 실행하지 않고 **검증 안 함(NOT_RUN)**으로 기록합니다. 이 경우 결과는 자동 반영되지 않습니다. 검증 명령이 테스트 없음(종료 코드 4·5)이나 명령 없음(126·127)으로 두 단계 연속 실패하면, BUILDER가 고칠 수 없는 문제이므로 미션을 끝내고 명령을 등록하라고 안내합니다.

검증 없이 끝난 단계가 통과하지 못하면 그 자리에서 한 번 "검증 안 함: … test_command를 등록한 뒤 다시 실행하세요"라고 알리고, 미션이 완료되지 못하면 마지막 메시지에도 같은 안내를 붙입니다. 테스트가 하위 폴더에만 있는 프로젝트(루트에 `tests/`가 없는 경우)는 자동 감지되지 않으니 명령을 등록해야 합니다.

검증 명령을 프로젝트 안이 아니라 Director 설정에 두는 이유는 BUILDER가 검증을 약하게 바꾸지 못하게 하기 위해서입니다.

Python 검증은 명령마다 별도의 임시 바이트코드 캐시를 사용합니다(2026-11-23).
같은 초 안에 같은 크기로 소스를 고쳐도 이전 `.pyc`로 검사하지 않도록 하며,
검증 명령이 실행한 하위 Python에도 적용됩니다. 기존 프로젝트·사용자 캐시는 지우지 않고,
Director가 만든 임시 캐시만 명령 종료 후 정리합니다. 콜드 import 비용은 늘 수 있지만
검사 명령·실패 판정·로그인 설정은 바꾸지 않습니다.

컴파일·린트 오류도 테스트 오류와 함께 HEAD·독립 리뷰어·다음 수정 작업으로 전달합니다.
각 검사에는 명령·실행 여부·종료 코드와 최대 4,000자의 출력 발췌를 붙입니다(세 검사 합계
최대 12,000자). 긴 로그는 앞뒤와 오류 문맥을 우선 포함하고 생략 여부를 표시합니다.
시간 초과 전의 표준 출력·오류 출력도 원본 검증 기록에 남깁니다. 발췌가 모든 오류를
담는 것은 아니므로 전체 출력은 원본 기록에서 확인할 수 있습니다. 로그는 지시가 아닌
증거로 다루며, 오류 전달 보완 때문에 기존 검토·안전 검사·수정 횟수 제한을 생략하지 않습니다.

## 설정

- **`config.yaml`:** 역할별 CLI, 타임아웃, 안전 상한(`max_files_changed`, `max_diff_lines`), 기본 검증 명령, 변경 이력 파일(`project_history`), 자율 모드와 프로필.
- **`config.local.yaml`:** 한 컴퓨터에만 맞는 설정. git에 올라가지 않으며 `config.yaml` 위에 병합됩니다.
- **`companion.json`:** 콘솔 포트(기본 8081)와 허용 프로젝트 목록.

```yaml

  timeout: 300        # 검증 명령 하나에 주는 시간(초). 처음 도는 swift test는 컴파일부터 합니다.
```

| 프로필 | 단계 수 | 자동 수정 | 빌더 시도 |
| --- | --- | --- | --- |
| `quick` | 2 | 1 | 2 |

`autonomy.auto_apply`는 `off`, `on_done`(목표 달성 판정 때만), `on_pass`(통과한 결과물이 있으면, 기본값) 중 하나입니다.

콘솔은 항상 `127.0.0.1`에만 열립니다. 상태를 바꾸는 요청은 로컬 출처 검사와 토큰(`data/solomon-bridge.token`, 본인만 읽을 수 있음)을 요구합니다.

## 프로젝트의 과거 결정

HEAD와 리뷰어는 이전 미션을 기억하지 못합니다. 그래서 프로젝트에 변경 이력 파일이 있으면 그 앞부분(기본 4,000자, 최신 항목이 위에 있다고 봄)을 HEAD(채팅과 첫 ORDER, 이후 단계 계획)와 리뷰어에게 보여 줍니다. HEAD에게는 목표가 요구하지 않는 한 기록된 결정을 뒤집는 계획을 세우지 말라고, 리뷰어에게는 그런 변경을 발견하면 지적하라고 지시합니다.

- **찾는 파일:** `CHANGELOG.md`, `docs/CHANGELOG.md`, `CHANGES.md`, `HISTORY.md`, `RELEASE_NOTES.md`, `DECISIONS.md`, `docs/DECISIONS.md` 순서로 프로젝트 루트에서 찾습니다. 루트에 없으면 하위 폴더 한 단계까지 보고, 그런 폴더가 하나뿐일 때만 씁니다.
- **읽는 곳:** 항상 프로젝트 원본에서 읽습니다. BUILDER가 방금 고친 작업본의 파일은 쓰지 않습니다.
- **바꾸기:** `config.yaml`의 `project_history.files`와 `max_chars`로 정합니다. `max_chars: 0`이면 끕니다.

## 후속 미션의 출발점

새 미션은 기본적으로 프로젝트의 현재 상태에서 시작합니다. 이전 미션의 작업본에서 이어 가는 것은 세 조건을 모두 만족할 때뿐입니다. 그 작업본이 검수를 통과했고, 아직 프로젝트에 반영되지 않았고, 그 미션이 시작된 뒤 프로젝트에 새 커밋이 없어야 합니다. 프로젝트가 그 사이 바뀌었다면 옛 작업본 위에서 작업해 새 변경을 되돌리는 일이 없도록 프로젝트에서 다시 시작합니다.

## 원본과 달라진 점

- **macOS 앱:** Swift·AppKit·WKWebView 전용 앱, 기본 폴더 선택 창, 종료 처리, 앱 아이콘.
- **검증 명령 감지:** 프로젝트가 실제로 지원하는 테스트를 골라 실행합니다. 원본은 모든 프로젝트에 `python -m pytest tests/`를 돌려 Swift·JS 프로젝트가 매 단계 실패했습니다.
- **검증 안 함 구분:** 통과·실패·실행 안 함을 구분하고, 실행 안 한 결과는 자동 반영하지 않습니다.
- **반영 보호:** 검수한 파일만 반영, 사용자 삭제는 충돌 처리, 이미 반영된 결과의 상태를 덮어쓰지 않음.
- **미션 판정:** 통과 단계가 없으면 완료로 표시하지 않음, 고칠 수 없는 검증 실패의 반복 중단, "변경할 것 없음" 답 허용, 후속 미션은 프로젝트 최신 상태 우선.
- **정지와 복구:** 지정한 미션의 프로세스만 종료, 서버 시작 시 남은 실행 정리. 정지 뒤에 재시도·리뷰·판정·반영이 이어지던 문제를 막았습니다(원본 저장소 PR #1의 edge0303이 실제 CLI 실행으로 찾은 결함이며, 접근 방식도 그 PR을 따랐습니다).
- **Claude 읽기 전용 실행:** 원본은 Claude Code를 제한 없이 실행해, Claude가 HEAD나 리뷰어일 때 작업본에서 명령을 실행하거나 사용자의 연결 앱에 닿을 수 있었습니다. 실행 인자는 `config.yaml`의 `claude_cli.read_only_args`로 바꿀 수 있습니다.
- **시간 초과 전환:** BUILDER가 시간 초과로 끝나면 같은 CLI를 다시 부르지 않고 바로 다른 CLI로 넘깁니다. 원본은 같은 CLI를 한 번 더 부른 뒤 넘겼습니다.
- **과거 결정 참고와 변경량 표시:** 프로젝트의 변경 이력을 HEAD와 리뷰어에게 보여 주고, 미션 전체 변경량을 완료 메시지에 적습니다.
- **저장소와 DB:** 저장소 안에 저장소를 만들지 않음, 프로젝트가 아닌 폴더(다운로드·응용 프로그램 등)에 저장소를 만들지 않음, SQLite WAL 모드와 대기 시간.
- **macOS 경로 처리:** 실행 파일 이름과 문서 경로를 macOS 형식으로도 올바로 읽습니다.
- **콘솔:** 솔로몬 연동 링크와 방송 모드를 걷어 냈고, 작업실 화면에서 스테이지 화면으로 돌아가는 링크를 넣었습니다.
- **원본 v3.2.0 반영 방식:** 과금 변수 제거, 범위 상한, 기본값(`resume_on_start: false`, `auto_apply: "off"`), 콘솔 세션, 프로젝트 밖 문서 제한, Antigravity 스위치를 가져왔습니다. Claude 읽기 전용 인자는 이 포크의 더 엄격한 설정(`core/claude_cli.py`)을 유지했습니다. 원본은 Antigravity를 끄면 콘솔 역할 버튼이 "서로 다른 AI 셋"을 요구해 역할을 저장할 수 없는데, 이 포크는 두 AI로 세 역할을 나누게 고쳤습니다. 새 설정(`antigravity.enabled`, `safety.reference_roots`)은 `config.local.yaml`로도 바꿀 수 있습니다.

## 알려진 한계

- **격리가 아닙니다.** AI가 쓴 테스트와 빌드 명령은 사용자 계정 권한 그대로 실행됩니다. git 작업본은 파일 변경을 원본과 나눌 뿐 샌드박스가 아니라서, 그 코드는 홈 폴더를 읽고 네트워크에 접근할 수 있습니다.
- **"구독만 사용"은 선언값입니다.** 기록의 `api_key_used: false`는 Director가 환경 변수의 키를 지우고 불렀다는 뜻이지, CLI가 실제로 무엇으로 과금됐는지 확인한 값이 아닙니다.
- **같은 계정의 다른 프로그램은 막지 못합니다.** 그런 프로그램은 `data/solomon-bridge.token`을 읽을 수 있습니다. 세션과 토큰은 포트에만 닿는 프로세스와 다른 웹 페이지를 막습니다.
- **Claude 역할도 프로젝트 파일은 읽습니다.** 쓰기·셸·MCP는 꺼 두었지만 읽기 도구로 프로젝트 안의 파일을 봅니다. Codex는 읽기 전용 샌드박스 정책을 따릅니다.
- 큰 변경도 BUILDER가 파일 내용을 JSON으로 제출하는 방식이라 CLI 출력 한도에 걸릴 수 있습니다.
- 각 CLI의 구독 한도에 그대로 묶입니다. 한도가 끝나면 다른 CLI로 넘어갑니다.
- 리뷰어와 HEAD가 같은 CLI로 몰리면 `REDUCED_INDEPENDENCE` 표시와 함께 진행합니다.
- 변경 줄 수 상한은 단계별로만 적용됩니다. 여러 단계에 걸친 미션 전체의 변경량에는 상한이 없고, 완료 메시지에 총량만 표시합니다.
- HEAD와 리뷰어가 보는 과거 결정은 변경 이력 파일의 앞부분뿐입니다. 이력 파일이 없거나 결정이 거기 적혀 있지 않으면 기존 규칙을 뒤집는 계획이 통과할 수 있으니, 결과를 반영하기 전에 변경 내용을 직접 확인하세요.
- 시간 초과한 CLI를 피하는 것은 한 단계 안에서만입니다. 다음 단계는 다시 기본 BUILDER로 시작합니다.
- 이 변경 이전에 끝난 실행은 검수 기록이 없어 반영이 거부됩니다. 다시 검수해야 합니다.
